# The SP7001 plug-in's screens and data

The SP7001 upgrade puts a second program in the KN7000's table flash: Key Soft Service's `XAPR`
plug-in, which program 942 finds at start-up and runs
([SP7001 Firmware: What Changed, and the Plug-in]({{ site.baseurl }}/kn7000-sp7001-firmware/#the-plug-in-in-table-flash)).
It brings **10 widget classes** of its own and **479 widgets on 31 screens**: SD SETTINGS, SELECT
SONG, SD JUKE BOX, SELECT C.L.S., CUSTOM LYRICS, and the naming and load / save windows. Since
2026-10-30 the disassembly types all of it the way the program's own GUI is typed
([KN7000 Menu Map]({{ site.baseurl }}/kn7000-menu-map/)): each widget is one line named by its
class, and a generated menu map lists every screen.

The lane notes are part 2 of
[`kn7000/notes/data-final/README.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/data-final/README.md)
(lane kn7000-final); the menu map is
[`kn7000/notes/sp7001-plugin-menu-map.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/sp7001-plugin-menu-map.md).

## Where it is

The plug-in is table 83 `0x3E8000`..`0x3FB5A0` (CPU `0x483E8000`), in `kn7000/src/sp7001/table.s`.
Its code, `0x3E803C`..`0x3EF6C5`, was already MN10300 assembly. Its data, `0x3EF6C5`..`0x3FB59C`
(48,855 bytes), held three generic pieces (33,127 + 4,274 + 9,224 bytes) and typed bits between
them. It is now `kn7000/src/sp7001/plugin/data/`, generated by
`tools/gen_data_s.py --profile sp7001plugin`, and `tools/gen_table_s.py --plugin-data` includes its
`data.s` in place of the old gaps:

```
make -C kn7000 plugin-src      # regenerate (runs both generators twice: a fixpoint)
make -C kn7000 verify-sp7001   # table 83 and program 942 rebuilt byte for byte
make -C kn7000 verify-gui-map  # the menu maps, this one included, are current
```

## How it registers its GUI with the host

The plug-in calls program 942 through 942's own registered Function table, as the HD-SX6 plug-in
calls the KN6000's ([KN6000 Program Data]({{ site.baseurl }}/kn6000-program-data/#the-hd-sx6-plug-in)).
`func_483E8071` makes the registrations:

```
mov (KssFrameworkObj), a0 / mov (0x1c, a0), a0 / mov (0xec, a0), a1 / calls (a1)
```

reads entry `0xEC / 4` of registry slot 1's table (16-byte registry records, `+0xC` the table; slot
1 is block 0's Function table), which is `RegisterObjectTable`, with the 16-byte {class, proc,
count, table} record on the stack and the slot in d0:

| slot              | what the plug-in registers                     |
|-------------------|------------------------------------------------|
| `0x2F0`           | the Viewable table (its 479 widget records)    |
| `0x2F8`           | the ResName table, parallel to it              |
| `0x2F1` / `0x2F9` | Functions and their names                      |
| `0x2F2` / `0x2FA` | ApFunctions and their names                    |
| `0x2F3` / `0x2FB` | MainFunctions and their names                  |
| `0x2F4`           | its 10 classes (`PLUG_Classes`)                |
| `0x2F5`           | events                                         |
| `0x2F6`           | methods                                        |

Registry block `0x2F0` is the plug-in's own; the classes and ids its records use from block 0 are
942's. **Initialised RAM:** `func_483E803E` clears `0xA48` bytes from `0x50299498` (`KssWorkRam`)
and copies `0x1498` bytes from `0x483FA104` (`KssRamImage`) to `0x50298000`. Widget records and the
variables their fields point at live there, labelled by their RAM addresses.

## What a record looks like

```
		AcKssList	Lst_SelDir, super=SelDir, next=SelDir_IndexEditSw1, prev=Tb_SelDir_ScreenName, flag=VF_Const, X=26, Y=38, W=510, H=172, color=CL_Silver, border=BD_3D_UP1, ap_func=FN_Ap_Lst_SelDir, auto_big_sel=1, font=3, columns=4, rows=12, ...
		AcIndexEditSw	SelDir_IndexEditSw1, super=SelDir, next=SelDir_IndexEditSw2, prev=Lst_SelDir, flag=VF_Const, X=124, Y=217, W=32, H=22, color=CL_Silver, border=BD_3D_UP1, index=8, fontcolor=CL_Black, editsw=ES_Bottom4, style=15
```

(`kn7000/src/sp7001/plugin/data/data_00.s`, abridged.) Links are object names, nested by
indentation; X / Y / W / H, colours and flags by constant name; captions inline; procedures by
`FN_` id; titles by `TT_` name, 942's `TT_PS`, `TT_SDCCUS` and `TT_SDAUDPLY` among them. The
plug-in's code spells its data operands with the same labels (`mov 0x483f8db8, d0` became
`mov PLUG_Classes, d0`).

## Open

- ~~`image_id=32872` and `icon=1` of the `KssBgScreen` records are numbers~~: traced by lane
  mn10300-formats (2026-10-31,
  [`kn7000/notes/mn10300-formats/README.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/mn10300-formats/README.md),
  section 4; probe `kss_bgscreen_ids.py`), and the plug-in's records now say both in their comments:
  - `icon` (1 in every record) is program 942's icon index. `KssBgScreenProc` (`0x483E9060`) answers
    its `+0x30` for `MT_GetIcon`, which 942's `TtlScreenProc` sends and passes to `DrawTitleBar` ->
    `DrawTitleBarOW` -> `DrawIcons`: entry 1 of the table flash's `ResIconTable`, `ResIcon001`, the
    icon 942's own `TtSoftver` / `TtDebug` screens show.
  - `image_id` (`0x8068` in every record) is read by nothing: no access of the plug-in's code at
    `+0x28` is 16 bits wide, `KssBgScreenProc` reads `+0x2C` and `+0x30` only, and 942's `Screen`
    class (40 bytes) ends before it. `0x8068` is no id of 942's resource-id trie. *[INFERENCE]* A field
    the plug-in's authors did not use; read as a Slide Show picture code (`0x8000 + n`), n = 104 would
    be past the 100 presets the slide show accepts.
- The RAM words the `str_adr` / `extension` fields point at hold values like `0x00C5CF2D` /
  `0x01514568` that are no address of this image or of the program; *[INFERENCE]* initial values
  the code overwrites. They are written `.long` with the comment "initial value".
