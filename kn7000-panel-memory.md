# KN6000 / KN7000 panel memories: what each byte is

A panel memory on the SX-KN6000 and SX-KN7000 is a copy of the instrument's live panel state. The
firmware recalls one by copying it over the live record in battery-backed SRAM (`0x84000020`), and
stores one by copying the other way. The same record is a PANEL MEMORY of the backup SRAM, a memory
of a `.PMT` file, a panel of an `.LSW` file, the settings bank of a demo song and the initial
settings a song keeps. Since 2026-10-29 the disassembly names its fields after the firmware
parameters that own them, found from the code that reads and writes them.

The lane notes are
[`notes/data-semantics-2026-10-29/kn67-field-names.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/notes/data-semantics-2026-10-29/kn67-field-names.md)
in the disassembly repository; the probes are
[`kn7000/notes/kn67-field-names-probes/`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/kn67-field-names-probes/README.md).
The names live in the shared includes, so every tree that uses them changed at once:

| file                                    | macros                                                                                                            |
|-----------------------------------------|-------------------------------------------------------------------------------------------------------------------|
| `kn7000/src/include/panel_memory.inc`   | `PMR_*`, the full panel record (generated by `floppy/tools/kd/gen_panel_macros.py`); `PM_*`, the one-touch record |
| `kn7000/src/include/voice_record.inc`   | `VOICE_*`, `SOUND_HEAD`, `SOUND_MOD`: the sound records                                                           |
| `floppy/tools/kn_song.inc`, `kn_sqt.py` | the song events and the song record                                                                               |

Users of those macros: the floppy describers ([Floppy Disk Files and Formats]({{ site.baseurl }}/floppy-disk-formats/)),
the CUSTOM banks ([Custom Style Memory]({{ site.baseurl }}/kn7000-custom-style-memory/)), the program
images' built-in panel memories and demo songs ([Program Data Region]({{ site.baseurl }}/kn7000-data-region/),
[KN6000 Program Data]({{ site.baseurl }}/kn6000-program-data/)) and the table flash's voice archive
([Table ROM]({{ site.baseurl }}/kn7000-table-rom/)).

## Recall and store

Library `func_4C021F33` (KN7000 lib `0x4C021F33`) takes a 1-based memory number n, computes the
record `0x84000824 + (n-1)/8 * 0x3A90 + 0x10 + (n-1)%8 * 0x750`, copies it over `0x84000020`
(`memcpy`, `0x750` bytes) and calls `func_4C01F98B`. `func_4C021EEE` is the store: the same copy the
other way. `func_4C01F98B` copies the eight 4-byte entries at record `+0xF4` into the work-RAM part
records `0x500D28C2 + i*0x4A`. The geometry (13 banks of 8, `0x2F950` bytes ending at the checksum
cell) is on [MEMORY DUMP Screen]({{ site.baseurl }}/kn7000-memory-dump-screen/).

## Every setting has a parameter id

Every live parameter is read and written through a 24-bit id. `GetM3Em` / `PutM3Em` look the id up
in `ResourceIdTrie` (KN7000 `0x4858B424`, walked by lib `func_4C01BB1A`; KN6000 `0x4C1935DC` and
KN2400 `0x48404E70`, each walked by its `ResourceIdFind`, named and typed by lane mn10300-rest: a root of
16 entries `{u32 target, u8 inner, u8 count, u16 0}`, taken by the id's nibbles from bit 20 down). A leaf is
`{u32 id, u16 type, u16 kind, u16 min, u16 max, u8 block, u8 offset, u8 mask, u8 shift}`. For type
0, `func_4C015602` dispatches on `kind` and reads through `func_4C01F153(block, offset, mask)`;
writes go through `func_4C01F200`, which then calls `func_4C01F8F4`, the accompaniment-entry
mirror. The block is a pointer from a table read by `func_4C021040` (KN7000 `0x4858D44C`; KN6000
`0x4C195520`, read by `func_4C031C94`), and **block n is the payload of the panel record's tag n**.
Part-scoped ids take the block from the id's top byte.

`m3em_param_map.py` measured 469 trie records on the KN7000 (314 of type 0) and 307 of type 0 on
the KN6000.

Many ids are MIDI messages. `func_48440533` builds an id as `(status & 0xF0) << 16 | controller`,
so `0xB0nnnn` is control change nn and `0xC00000` program change; *[INFERENCE]* `0xB080nn` is RPN nn
(its ranges are 0..12 for RPN 0, 40..88 for RPN 2). Names for the other ids come from their callers
(`m3em_callers.py`: 1,303 calls with a literal id, 213 distinct ids), from the GUI grids of the
[menu map]({{ site.baseurl }}/kn7000-menu-map/) (their captions and `func=` handlers), and from the
song-event trace.

## The record: tags and parts

The record is a list of tag / length blocks, ending with `0xFF 0xFF`. The MIDI part grid's row
table (`0x48626C14`, read by `MidiPartGrid`) names the parts:

| tags                         | block                                                                                                  |
|------------------------------|--------------------------------------------------------------------------------------------------------|
| `0x00`-`0x0F`                | PART 1-16, 72-byte part records (`PMR_PART`)                                                           |
| `0x10`-`0x12`                | RIGHT 1, RIGHT 2, LEFT                                                                                 |
| `0x13`-`0x1A`                | ACCOMP 1-5, BASS, DRUMS 1, DRUMS 2: 4-byte entries (`PMR_ENTRY`); their part records are in work RAM   |
| `0x1B`                       | CHORD                                                                                                  |
| `0x1F`                       | B.PEDAL (KN7000; from the song-track names at `0x486773D8`)                                            |
| `0x40`                       | the memory's name (`PMR_NAME_HEAD`, the text, `PMR_NAME_TAIL`)                                         |
| `0x41`-`0x4D`                | the panel sections (`PMR_41_8` .. `PMR_4D_14`, the suffix is the payload length)                       |
| `0x50`-`0x52`, `0x60`-`0x68` | past the `0x750`-byte record image: `PMR_50_8`, `PMR_51_14`, `PMR_52_40` / `PMR_52_46`, `PMR_60_20` .. |

**What keeps a placeholder name, and why.**

- `m<id>` (about 60 fields): the parameter id is known, so the field can be searched for in the
  probes' output and in the code, but no caller or screen caption says what it means. Examples are
  the part's `ctl_bits` / `tg_bits` bits `0x204080`-`0x204088` (sent to the tone generator as TG
  codes), the second sound triple `0x204020` at part `+0x3C`, the MIDI filter bits of tag `0x47`
  (the MIDI control grid builds those ids at run time, so the literal-call probe does not see them),
  and the vocalist and mic bytes of tags `0x4A` / `0x4B`.
- `p<hex>` / `x<hex>`: no parameter record covers the byte (part `+0x06`..`+0x0A`, `+0x21`, `+0x2B`,
  `+0x44`..`+0x47`; most of tags `0x41`, `0x48` and `0x60`-`0x68`). Nothing in the parameter layer
  reads them; a direct reader elsewhere may exist.

**KN6000.** The two type-0 maps (`m3em_param_map.py --table`, both models) agree on every part field
except the KN7000-only ones (scale bits `0x2000B0`-`BF` at part `+0x38` / `+0x39`, tremulant
`0x2000A2` at `+0x23`, APC reverb `0x00E030`-`3F` at tag `0x44` `+0x0C`..`+0x13`) and some ranges.
The KN6000 has more foot-controller functions (`0x004008`-`0x004041` in tag `0x48`), which keep
`x<hex>` names. Its record is `0x700` bytes, not `0x750`.

## The song record keeps an image of the same SRAM

`func_4C01F153`, in mode bit 0 (the `GetM3Sqf` / `PutM3Sqf` "Sqf" bank), reads a parameter at
`Rec8E0Field120Ptr` (record 0) `+ (block - 0x84000000)`. So song record `+0x120` onward is an image
of backup SRAM `0x84000000 + (offset - 0x120)`: `+0x140` is the song's panel memory (the image of
the live record), and the tail after it is block `0x52`, 46 bytes on the KN6000 (the record's end)
and 40 on the KN7000, followed by the images of blocks `0x50`, `0x51` and the start of `0x60`, whose
tag / length bytes the song copy does not keep. All 605 song records type that block as `PMR_52_40`
/ `PMR_52_46`. `+0x07`..`+0xCF` and `+0x100`..`+0x11F` stay rows: no reader was traced.

The song events now follow the firmware's own per-status length table (`0x485B9328`, read by
`func_4845BC5B`; the player tick steps each track through it). It agrees with the lengths measured
on every status the 27 disks hold, and adds `0x84` (bar), `0x8A` (PIC), `0xA2` / `0xA3` and `0xF4`;
`0xB1`-`0xBF` are not events. The macros' parameters are the event layouts: `sq_cc` {part, cc,
value}, `sq_a` {part, flags, id big-endian, value}, `sq_note` {key, velocity, u16 duration}.

## The sound records

A tone record (a `0x54`-byte head and its `0x7A`-byte element units) and the first `0x23C` bytes of
a SOUND EDIT record have the same layout: `TgPartAuxRecBuild` copies one onto the other. So the
table flash's voice archive, the CUSTOM banks and the SOUND EDIT records share `SOUND_HEAD`,
`SOUND_MOD`, `VOICE_HEAD_TAIL`, `VOICE_SUB` and `VOICE_ELEM` (tables 84, 83 and 80 rebuild
byte-identically).

The `Tg*` routines read a "desc2" at librec `+0x3C` with offsets up to `+0x4C`, which did not fit a
`0x1C`-byte sub-record. On the melodic path the staging routine `TgElemStageFresh` (lib
`0x4C034927`) stores the `0x7A` unit there, the same pointer `TgPartAuxRecBuild` copies into a SOUND
EDIT record; only the table-tone staging stores a sub-record at `+0x3C`. So the desc2 readers name
the unit's fields: level offset and velocity sense, the pitch EG (`+0x0B`..`+0x17`), the effect
sends and the glide bit (`+0x18` / `+0x19`), key follow, the velocity and key fade zones
(`+0x20`..`+0x27`), the amp EG rates, breakpoints and sensitivities (`+0x28`..`+0x36`), CUTOFF
ADJUST and the filter EG (`+0x3E`..`+0x4C`). `SOUND_HEAD` names the tone class, the modulation
source, the tone type and the EG flag; `VOICE_SUB` the element reference (`+1`..`+3`, which the
table-tone staging passes to `TgPartElemProgramApplyIdxSel`); `VOICE_ELEM` the three velocity split
points and six 5-byte layers whose first bytes go to `VoiceParamRecFetchBanked`.

Not named: the unit's `+0x04`..`+0x06` (SOUND EDIT reads and writes them through
`TgPartAuxMod04Get` and its siblings, but their meaning is not traced), and the bytes no traced
routine reads. Which tone generator (MAIN or SUB) each zone's side bit `0x400` / `0x800` selects is
not traced either: `TgVoiceSideSelect` maps class 1 / 2 kits to `0x400` and 3 / 4 to `0x800`.

## IC21: what a KN7000 keeps in its custom-data flash

The KN7000 keeps the data its owner can change but Initial Setting must not touch in a 2 MB flash,
IC21, at `0x96800000`. One real chip is rebuilt byte for byte: the IC21 of the project owner's
KN7000 (program 893, table 80), read with the instrument's own [ROM dumper]({{ site.baseurl }}/kn7000-rom-dumper/)
on 2026-10-19, twice, with identical results. Until 2026-10-31 that read was kept out of the trees as
personal data; on that day the owner decided it becomes typed source, and lane ic21-own made it so:
[`kn7000/src/ic21own/ic21.s`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/src/ic21own/ic21.s), whose header says what each region holds, and [`kn7000/notes/ic21-own/README.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/ic21-own/README.md). The read itself
stays private: `make -C kn7000 verify-ic21-own` (in `make gate-kn7000`) copies it, git-ignored and
SHA-1-checked, and rebuilds all 2 MB from the source.

| CPU          | chip offsets        | contents                                                                                        |
|--------------|---------------------|-------------------------------------------------------------------------------------------------|
| `0x96804000` | `0x04000`-`0x0427F` | the three USER MIDI SETTINGs, the layout of a `.MD` file                                        |
| `0x96804280` | `0x04280`-`0x04A6F` | the CUSTOM PANEL: a PANEL MEMORY record (43 records) and a second list (7)                      |
| `0x96804A70` | `0x04A70`-`0x04AA3` | 26 halfwords of system settings (language, display times, data protect ...)                     |
| `0x96806000` | `0x06000`-`0x07FFF` | `A5 A5 5A 5A` x 2048: the pattern the service ROM test writes and reads back                    |
| `0x96810000` | `0x10000`-`0x10197` | FAVORITES: four banks of ten items (a `.FAV` file)                                              |
| `0x96811000` | `0x11000`-`0x15441` | the HOME PAGE: its layout record and a 160 x 100 BMP (a `.HMP` file)                            |
| `0x96820000` | `0x20000`-`0xF8F16` | the CUSTOM STYLE memory: 20 styles with their One Touch Settings (an `.AST` file is all of it)  |

Everything else is erased. *[INFERENCE]* The boundaries fit the sector map of a bottom-boot 16 Mbit
AMD flash (16 KB, 8 KB, 8 KB, 32 KB, then 64 KB sectors), so each block starts a sector of its own.

**The settings image at `0x96804000`** (0xAA4 bytes). The table's help text says what it is: "User
MIDI Settings, Help language, and Rhythm Custom etc. are not affected by Initial Setting"
(`HelpTextEn41_0`). `func_4C024247` copies the whole image to RAM `0x500D2B14`; `func_4C024030(n)`
re-reads one section n and `func_4C024000(n)` programs it back. Both jump through a table of 23 cases
(`func_4C024030_Table`, `func_4C024000_Table`); the RAM and flash address of every case, read from the
image by the probe `section_map.py` (lane ic21-rest, 2026-10-31, which corrected an earlier order of
the sections):

| n      | offset             | size         | what                             | written back by                     |
|--------|--------------------|--------------|----------------------------------|-------------------------------------|
| 0      | `+0x000`           | 0x10         | `.MD` header                     |                                     |
| 1      | `+0x010`           | 0xC0         | parameter-id list                |                                     |
| 2..4   | `+0x0D0` ...       | 0x90 each    | USER MIDI SETTING 1..3           | `func_484C4144`                     |
| 5      | `+0xA70`           | 2            | language                         | LangSetFlashFunc, LangSetFlashFunc2 |
| 6      | `+0xA72`           | 0xC          | the six display times            | MainTimeFlashFunc, MainSysControl   |
| 7      | `+0xA7E`           | 4            | jump_insert, file_priority       | SetupFlashFunc                      |
| 8      | `+0xA82`           | 8            | para_load1..4                    | MainFlashFunc                       |
| 9      | `+0xA8A`           | 8            | wall_home1..4                    | MainWallSetFlashFunc                |
| 10     | `+0xA92`           | 2            | contrast                         | FN_TtContrast (`func_4854E5C6`)     |
| 11, 12 | `+0xA94`, `+0xA96` | 2 each       | r_a94, r_a96                     | nothing                             |
| 13, 14 | `+0x280`           | 0x750, 0x7F0 | the CUSTOM PANEL, short or whole | `func_4C021F7F`, `func_4C021FD9`    |
| 15     | `+0xA98`           | 2            | data_protect                     | MainDtPrtFlashFunc                  |

| 18     | `+0xA9C`           | 2            | acc_reverb_mask                  | nothing                             |

 At boot `func_4C023EC9` compares the
image's first 3 bytes with `"JK "` and, when they differ, rebuilds the image from ROM and programs it:
the `.MD` part from `Str_JK_6` and its blocks, the CUSTOM PANEL from `Str_empty_1431` (0x7F0 bytes),
the 26 halfwords from `func_4C023EC9_Table` and `func_4C023F9B_Table`. It then resets the home page
(`HpFlashWriteDefaults`) and the favorites. The FAVORITES and HOME PAGE records are checked the same
way by their own `JK` signatures.

- **USER MIDI SETTINGs** (`+0x000`). The header is `UMD_HEADER` (`"JK "`, then the offset and size of
  the id list and of a setting, and the count, 3), then a list of 44 parameter ids (`UMD_PARAM`), then
  three settings of 0x90 bytes. A part parameter takes 32 bytes (value n for part n), any other one
  byte: 137 values per setting. The parameters are LOCAL, MIDI CHANNEL and MIDI OCTAVE per part, the
  MIDI CONTROL channel and the MIDI message filters.
- **The CUSTOM PANEL** (`+0x280`, 0x7F0 bytes) is "a special Panel Memory in which you can store your
  favorite Panel Memory settings ... Even initializing the KN will not delete the Custom Panel"
  (`HelpTextEn35_0`): the live panel state `0x84000020`, stored or recalled by `func_4C021903`, in the
  PANEL MEMORY format of this page, every record spelled with its `PMR_*` macro. It is 0x750 bytes
  (43 tag / length records ended by FF FF), or 0x7F0 with a second list of 7 records (tags 0x52, 0x50,
  0x51, 0x60, 0x61, 0x62, 0x68) when `cus_mem_mode` (`+0xA9A`) is non-zero. The CUSTOM PANEL MODE
  screen offers "PANEL MEMORY" and "ALL PANEL", in that order, and `CusMemModeBoxProc` frames the box
  `cus_mem_mode` indexes: 0 = PANEL MEMORY, 1 = ALL PANEL (`HelpTextEn35_1`'s choice "whether to load
  all panel settings or to load panel memory parameters"). This unit has 1. The second list is the
  panel state that no panel memory holds, which ALL PANEL adds: tag 0x52 the current PANEL MEMORY
  number, the DSP unit numbers and the MONO 1 / 2 output parts; tag 0x50 the tone-generator mode
  (`AcTGModeSelProc`); tag 0x51 the touch sensitivity (`TchSensGridCheck`); tags 0x60-0x62 and 0x68,
  whose bytes no parameter record covers.
- **System settings** (`+0xA70`, `USR_SETUP`): 26 halfwords, RAM `0x500D3584`..`0x500D35B7`, each named
  after the routines that read its RAM copy (language: `CheckLanguage`, `AcLanguageTextProc`; data
  protect: `DataProtectGridCheck`); `user_settings.inc` gives every field with its reader. Named by lane
  ic21-rest:
  - **the six display times** (`+0xA72`..`+0xA7D`): the DISPLAY TIME OUT screen; `DispTimeSetGridCheck`
    maps rows 2..7 of its grid to them in the order of the row captions: SAVE REMINDER, 'COMPLETED'
    MESSAGE, ARE YOU SURE?, ERROR MESSAGE, SOUND/RHYTHM SELECT, EASY SETTING;
  - **`contrast`** (`+0xA92`): the LCD contrast. FN_TtContrast re-reads section 10 and hands the value to
    `func_484ABAA9`, which clamps it to 3..100 and sends panel-CPU command 0x1C with
    `func_484ABAA9_Table[value]`. This unit has 59, the default 50;
  - **`acc_reverb_mask`** (`+0xA9C`): one bit per accompaniment part, bits 0-7 = ACCOMP1-5, BASS, DRUMS1,
    DRUMS2 (part tags 0x13-0x1A). `func_4C027803`, the CC91 (reverb depth) case of the part-CC table
    `func_4C024DD8_Records_4`, sends a part's CC91 value only when its bit is set, else 0. The default
    is 0xFF and nothing writes the field;
  - **`r_a94`, `r_a96`** (`+0xA94`, `+0xA96`): no routine of programs 893, 935 or 941 names their RAM
    address except the section code itself, and nothing writes their sections back. They stay at the
    boot defaults, 0 and 1.

**The flash test** at `0x96806000`. `func_4849FCF2`, one step of the ROM test (`MainRomTestFunc`),
programs a buffer of `0x5A5AA5A5` there in 0x80-byte chunks, 0x2000 bytes in its long form (0x320
otherwise), and reads it back; nothing erases it afterwards. The 0x2000 bytes on this chip say the
long form of the test ran on this unit. The source spells them as 64 `FLASH_TEST_CHUNK`s. The long form
is the TEST MENU's page 1, ROM DEVICE TEST ("PROGRAM ROM: IC16", "RHYTHM ROM: IC18 (IC20)", "CUSTOM
FLASH: IC21"): `func_4849FC1A` answers 1 only when the test state buffer (RAM `0x5006BA20`) holds title
0xFC (`TT_TESTMENU`) at `+0x1F9` and `func_4849FBE4_Table[page]` = 1 at `+0x1F8`. Run from the `stest1`-`stest7`
screens (titles 0xF4-0xFA), the test writes the short 0x320 bytes (lane ic21-rest).

**FAVORITES** at `0x96810000` (0x198 bytes): `FAV_HEADER` (`"JK "` and a u32 stamp), then four banks
(`FAV_BANK`) of a 16-character name, a u32 and ten `{u32 kind, u32 value}` items (`FAV_ITEM`), which
`AcFavoriteProc` dispatches by kind through `AcFavoriteProc_Table`. The u32 at bank `+0x10` is the
NUL that ends the name, padded to a word. What each kind's handler draws and recalls (lane ic21-rest;
the source spells the kinds with the `FAVK_*` names of `user_settings.inc`):

| kind             | handler         | name              | the item                                                                                                              |
|------------------|-----------------|-------------------|-----------------------------------------------------------------------------------------------------------------------|
| 0, 1, and 10..15 | `func_4849D4D4` | `FAVK_NONE`       | nothing: an empty box                                                                                                 |
| 2                | `func_4849D575` | `FAVK_SETTING`    | "FAVORITES SETTING": opens the FAVORITES SETTING page; value 0. Every bank ends with it                               |
| 3                | `func_4849D6A8` | `FAVK_SOUND`      | a sound `{program, bank LSB, bank MSB}`, put to parameter 0xC00000 of the selected part                               |
| 4                | `func_4849DAAF` | `FAVK_RHYTHM`     | a rhythm: its id, put to parameter 0xC000                                                                             |
| 5                | `func_4849DCF9` | `FAVK_STYLIST`    | a MUSIC STYLIST setup: below 0x438 one of `StyleRecordTable`'s 1,080, above it the user's                             |
| 6                | `func_4849DE62` | `FAVK_MENU`       | a menu page: an index into `func_4849DE62_Table` (114 records: "SOUND MENU", "SOUND PART SETTING", "MIXER" ...)       |
| 7                | `func_4849E0E0` | `FAVK_PANIC`      | "PANIC": parameter 0x600004 := 0; value 0                                                                             |
| 8                | `func_4849E193` | `FAVK_MUTE_KEYS`  | "MUTE KEYS : ON / OFF": toggles parameter 0x600005; value 0                                                           |
| 9                | `func_4849E303` | `FAVK_SOUND_MODE` | the sound mode: parameter 8 := value; 0 "NX SOUND ON", 2 "GM LEVEL2 ON"                                               |

**HOME PAGE** at `0x96811000` (0x4442 bytes, the whole `.HMP` file, as `HmpBlobGet` returns it): the
0x18C-byte record and the BMP. `HP_HEADER` holds the home-page type, which `AcHpTypeEditProc` keeps in
0..5 and uses to index `TtNormal_Records`: 0 DEFAULT, 1 DEFAULT WITH PICTURE, 2-4 PRESET 1-3, 5 USER,
the record's own parts. Then come 64 parts of 6 bytes (`HP_PART`, `{u16 kind, s16 x, s16 y}`). The kind
indexes `TtNormal_Table`, 49 part kinds named by the strings of `Text_TITLE_BAR_NORM` (title bars,
balance, combinations, sounds, rhythm, tempo, chord, split point, pads, panel memory, picture, song,
favorites bank, effects, foot switch and controller ...; `HPK_*`); kind 0x31 (`HPK_NONE`) is an unused
part. x and y are the part's grid cell, and y = -1 is the row above the grid: every preset layout and
the factory record put their TITLE BAR part there.

At boot FAVORITES is compared with the ROM template `func_4849EDEB_Table` (the signature, then the u32
stamp) and rewritten from it when either differs.

**This unit's chip.** Its MIDI settings and favorites are the factory ones byte for byte (`02UMDINI.MD`
and `03FAVINI.FAV` of the Initial Data Disk, and the defaults in program 893), and so is its home-page
picture (`Bmp_48743E5C`, which the source includes as a committed BMP). Its custom panel (1,935 of
2,032 bytes equal the default) and its home-page layout (type 0 with three parts: TITLE BAR NORM at
(0, -1), RIGHT COMBI 1 at (8, 0) and BALANCE NORM 1 at (0, 4), where the factory file has type 5 and
twelve) are his own. Its 20 custom styles are styles of the KN5000 that came through a KN6000 CUSTOM
file ([Custom Style Memory]({{ site.baseurl }}/kn7000-custom-style-memory/#a-real-units-bank-the-owners-ic21)).

**Corrected 2026-10-31.** The first analysis of this read (2026-10-19) took `0x04280`-`0x04ABF` for
"2 KB more MIDI-setting records". It is the CUSTOM PANEL and the system settings, and the used part ends
at `0x04AA3`.
