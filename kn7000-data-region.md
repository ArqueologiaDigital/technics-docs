# KN7000: the program's data region, typed from the code that reads it

Program build 941's data region is file `0x186000`..`0x3B8000` (CPU `0x48586000`..`0x487B8000`),
plus the `0xFD1` bytes before the library image: 2,306,001 bytes of tables, records, text, pictures
and compressed songs between code region 1 and the MILK kernel
([Firmware Images]({{ site.baseurl }}/kn7000-firmware/#region-map)). Until 2026-10-29 the
disassembly held it as three `.incbin_range` lines and a typed palette. It is now
`kn7000/src/program/data/`, generated by `kn7000/tools/gen_data_s.py`, and the image stays
byte-identical (`make -C kn7000 verify`). Builds 942 (SP7001), 935 and 893 get the same from the
same generator (`--profile sp7001 / b935 / b893`, `src/<build>/program/data/`,
`make verify-sp7001 verify-935 verify-893`).

The GUI part of the region, the 8,509 widget records and their classes, is on
[KN7000 Menu Map]({{ site.baseurl }}/kn7000-menu-map/). This page covers the rest. Three lanes of
the data-semantics effort did the work; their notes, in the disassembly repository, are the
reference:

| lane             | notes                                                                                                                                                   | what it added                                                                                    |
|------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------|
| gui-kn7000       | [`kn7000/notes/gui-data-region/README.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/gui-data-region/README.md) | the GUI, demo songs, the built-in style, jump tables, reader tables, sparse maps, panel memories |
| kn7000-data-rest | [`kn7000/notes/data-rest/README.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/data-rest/README.md)             | the reader walk; struct arrays and the records their pointers lead to; DSP records, bitmaps      |
| kn7000-final     | [`kn7000/notes/data-final/README.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/data-final/README.md)           | the extended walk; the resource-id trie, SupportClass table, SysEx strings; the SP7001 plug-in   |

## Structures that have a format of their own

- **The built-in demo songs.** The 30 zlib streams of each build are its 10 demo songs, three
  streams each. `func_48457350` (d0 = the song) takes song n's streams from three 12-entry tables
  in the initialised RAM and inflates them with `func_48533758`: the song record into
  `Rec8E0TablePtr(0)` (`0x8E0` bytes), the event memory into `0x5003D36C` (`0x9800` bytes) and a
  panel-memory bank. They are the formats of the floppies' `.SQT` and `.PMT` files, so the floppy
  describers type them, event by event and record by record
  ([Floppy Disk Files and Formats]({{ site.baseurl }}/floppy-disk-formats/#songs-sqt)), inside
  `.zlib 6` blocks: kn7asm compresses them with Python's zlib, which reproduces all 30 streams
  byte-exactly.
- **The program's own "Technics Rhythms" resource.** `TechnicsRhythmsResource` (941 `0x48729988`)
  has IC18's format ([Rhythm ROM (IC18)]({{ site.baseurl }}/kn7000-rhythm-rom/)) with a single
  style, "8 Beat 1", the fallback. `tools/program_rhythm.py` types it with IC18's macros: header,
  count block, the 2048-entry index, the tables, the 8 count-in patterns, the style record and its
  20 variations, every event one line.
- **Built-in panel memories.** The `0x486C`..`0x4870` region holds 103 (941) built-in PANEL
  MEMORY records: tag / length lists that start with the name record, hold 43 records and fill
  exactly `0x750` bytes, several behind a 16-character bank name. They are `PMR_*` lines, the same
  macros as the floppies' `.PMT` files ([Panel Memory Records]({{ site.baseurl }}/kn7000-panel-memory/)).
- **The tone generator's curves.** The region `0x486C0000`..`0x486F0000` is not style data: it is
  the tone generator's curve and level tables, read by the `Tg*` library routines
  (`TgElemNoteOnStd_Table` is the curve at `0x486D1F54`, 128 x u16).
- **The effects-DSP download records**, 80 of them, block by block, each program-memory word with
  its SHARC instruction ([Effects DSP]({{ site.baseurl }}/kn7000-effects-dsp/)).
- **Bitmaps.** Procedures that answer `MT_GetBitmapData` / `Width` / `Height` / `Palette` /
  `MT_GetBitCount` give the bitmap resources, and pixels handed to `DrawBitmapSP` and its variants
  with a constant size give more; they are indexed PNGs in `<data dir>/media/`, packed back by
  `tools/table_png.py` at build time. The 8 JPEG and 2 BMP files the region holds are whole files.

## Typed from the code that reads it

Most of the region has no format of its own: it is tables and records that only the code
explains. `kn7000/tools/data_readers.py` walks the converted code function by function, with a
symbolic value per register:

| value      | meaning                                                                            |
|------------|------------------------------------------------------------------------------------|
| `C(c)`     | a constant                                                                         |
| `A(x)`     | the address x (a data label, `Label+N`, or a number)                               |
| `S(s)`     | an unknown index times s (`mul` / `mulu` by a constant, `asl`, `asl2`, `add r, r`) |
| `I(b,s,o)` | b + index * s + o: field o of an array of s-byte records at b                      |
| `P(key,o)` | a pointer loaded from the 32-bit field `key`, plus o                               |
| `D(key,o)` | a function's own d0 / d1 argument: a pointer if it is dereferenced, else an index  |

Every load, store and call argument through such a register is an access, with its width and
signedness (an `extb` / `exth` right after the load). A function's accesses through its own
arguments are carried into every caller that passes a data address in them, so a record handed to
a helper is typed by what the helper reads. Every structure found is also checked against the
bytes.

**Struct arrays.** An access through `base + index * stride + offset` makes an array of
`stride`-byte records at `base`. Each record kind is one macro in `<data dir>/data_structs.inc`,
whose header lists every field, its type and its first readers, with the instruction:

```
# MusicStylistSetup: 24-byte records (StyleRecordTable, 1080 records); fields, and what reads them:
#   +0   panel        ptr            func_4847B18C 0x4847B18C `mov (d2, a2), a0`; AcCategoryListBoxProc 0x4847B2AE `mov (d0, a0), d0` (+10)
#   +4   name         ptr            MssNameFunc 0x4847AFDD `mov (4, a0), a1`; func_4847B14B 0x4847B14B `mov (4, a0), a1` (+3)
#   +8   genre        u16            AcCategoryListBoxProc 0x4847B2AE `movhu (8, a1), d0`; func_4847BA42 0x4847BA42 `movhu (8, a1), d0` (+9)
#   ...
#   +22  x22          u8[2]          no reader seen
```

**Records a pointer leads to.** When the code loads a pointer from a typed field and reads through
it, the targets of that field are records too, typed by the offsets those reads use. When the
targets lie a constant distance apart, that distance is the record size. `StyleRecordTable`'s field
`+0` points at 1,037 records of 160 bytes, one per built-in style's panel settings
(`MusicStylistPanelData`). Fields no traced reader names keep offset names (f / p / s / a / x +
offset), with every reader in the macro header; `tools/data_struct_names.py` names the kinds whose
role is known.

**The extended walk** (lane kn7000-final, `Reader(ext=True)`, the four KN7000 program builds only)
follows what the plain walk lost:

| rule              | what it follows                                                                                                | example                                                                                 |
|-------------------|----------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------|
| stack slots       | `mov aN, (8, sp)` ... `mov (8, sp), a0`: a slot keeps the value stored                                         | `func_484C4229` spills a value block to `(0x2c, sp)` and reads it with `movbu (a0), d2` |
| joins             | a label that paths reach with different data addresses holds "one of them"; reads through it are reads of each | `func_484C01F1`, a 260-way switch that leaves one descriptor's address in `(0, sp)`     |
| return values     | what a function returns in a0: one of a set of addresses, or a pointer loaded from a typed field               | `func_484C01F1` (260 records), `func_485831BA` (an entry of `func_485831BA_Table`)      |
| named loop labels | a label is a function start only at its header, or where nothing falls in and no branch reaches it             | `DrawIcons_Impl_RowLoop` keeps a3 = `DrawIcons_PixelPairTable`                          |
| loop bodies       | a label reached only by a backward branch keeps the frame's slots                                              | `func_485831DC`'s `movbu (d1, a0), d2` over a demo stream                               |
| bounds            | a load whose source the walk does not know drops the bound an earlier `cmp` gave the register                  | `DrawIcons_PixelPairTable` is 256 entries, not the 240 of `cmp 0xf0, d0`                |

On program 941 the plain walk sees 22,372 distinct accesses and the extended one 26,677
(`kn7000/notes/data-final-probes/reader_ext_stats.py`); 126 functions return one of a set of data
addresses.

With it come new passes of `gen_data_s.py`:

| pass              | what it types                                                                                                         | evidence                                                         |
|-------------------|-----------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------|
| `support_classes` | the SupportClass table (registry slot `0xD`, 54 entries and an empty one) as `SUPPORT_CLASS proc, x4, propsize, data` | `InitSptClassTable` registers it; `SupportClassProc` reads it    |
| `resource_trie`   | the resource-id trie: 177 tables, 940 entries, 7,400 bytes, as `RES_TRIE_ENTRY target, inner, count`                  | `func_4C01BB1A`: nibble-indexed 8-byte entries, inner 0 = a leaf |
| `sysex_strings`   | MIDI SysEx messages a typed pointer points at (`0xF0`, data below `0x80`, `0xF7`; `0x50` = Matsushita), one row each  | the framing, and the pointer fields that hold them               |
| `copied_blocks`   | a data address passed to memcpy / memcmp / strncmp / strncpy with a constant length: that many bytes                  | the call's a0 / a1 and d0, cited in the header                   |
| `pointer_runs`    | aligned runs of 3 or more words that are each 0 or an address of the region: `.long Label`                            | *[INFERENCE]* by value; the header says no reader was traced     |
| `ptr_records`     | records one function selects: `<func>_Result` / `<func>_Selected`; short records as `<kind>_s<N>` size variants       | the reads through the selected value                             |

**The resource-id trie** is the table every live panel parameter goes through: `GetM3Em` /
`PutM3Em` look a 24-bit parameter id up in `ResourceIdTrie` (`0x4858B424`, inside the typed
`ResourceIdTrieNode_485897BC`), a tree indexed by the id's nibbles, whose 469 leaves say which byte
of the live panel record holds the parameter. What those leaves name is on
[Panel Memory Records]({{ site.baseurl }}/kn7000-panel-memory/).

Other examples: `TechniChordCompute_Table_2` is the chord-type switch of `TechniChordCompute`
(`0x48472EBA`), 42 code pointers (a table that holds code addresses spells each target `loc_<ADDR>`,
and `code_refs.txt` makes the code generator label it); the effect names and fixed-width value
strings ("  0.1   ", "   10 ms") are string arrays; `{u32 key, code address}` runs are dispatch
tables, with a MILK-id key spelled by its name.

## What is left: the census

The instrument is `scripts/analysis/data_incbin_census.py`
([ROM Reconstruction]({{ site.baseurl }}/rom-reconstruction/#the-data-include-census)). Its first
committed snapshot,
[`docs/coverage/data-incbin-2026-10-30-01.txt`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/docs/coverage/data-incbin-2026-10-30-01.txt)
(measured at disassembly `28bad682a`), reads for the four program builds (count / bytes):

| tree             | generated     | media           | opaque        | generic n | generic bytes |
|------------------|---------------|-----------------|---------------|-----------|---------------|
| `kn7000-program` | 87 / 162,942  | 10 / 58,992     | 4298 / 82,196 | 177       | 2,948         |
| `kn7000-sp7001`  | 526 / 462,454 | 169 / 1,375,301 | 4321 / 80,480 | 179       | 3,044         |
| `kn7000-b935`    | 87 / 162,942  | 10 / 58,992     | 4309 / 83,003 | 179       | 3,044         |
| `kn7000-b893`    | 87 / 162,942  | 10 / 58,992     | 4303 / 81,886 | 176       | 2,944         |

(`kn7000-sp7001` also holds table build 83, whose media and generated items are most of its first
two columns.) For comparison: before the work the program tree was 3 generic entries of 2,563,794
bytes; after lane gui-kn7000 6,294 pieces of 793,436 bytes; after kn7000-data-rest 433 pieces of
17,416 bytes; now 177 pieces of 2,948 bytes. `gen_data_s.py` types 2,106,173 of the region's
2,306,001 bytes in build 941 (91.3%). The generated column is the bitmaps
(`census: generated -- tools/table_png.py`).

**Generic** means read but not typed: each such piece holds an address some instruction reads,
loads as a base or passes to a call, and no pass turns it into a type yet. In 941:

- records of the 260-way switch (`func_484C01F1`) whose pointer fields point into their own tail,
  so their room is less than any size variant's fields (30 bytes each);
- RAM-image tables read with an index from a RAM pointer (`data_500077A4` and after, 208 bytes;
  `0x5000102C` / `0x50001120`, 124 / 120 bytes of zeros the code fills);
- small tables read once through a computed base (the tail of `func_4841493C_Table`, 72 bytes; two
  64-byte colour tables at `0x4859E484` / `0x485EFF04`; `SjisMissingGlyph`'s 32 bytes);
- blocks handed to library routines whose layout the callee decides at run time.

**Opaque** (`census: opaque -- unknown-dump`) means that no load, store, base or call argument of
the converted code lands in the bytes under the extended walk, and the line says whether a typed
pointer or a code immediate still holds their address. `kn7000/notes/data-final-probes/opaque_holders.py`
also searched the whole image for any 32-bit word, at any alignment, holding an address in the
piece or up to 64 bytes before it. The biggest in 941:

| piece                                       | bytes | holders | what the bytes look like                                                                 |
|---------------------------------------------|-------|---------|------------------------------------------------------------------------------------------|
| `0x48730AB3`                                | 2,101 | 0       | 7-byte groups `xx 90 xx xx xx 00 00`; no word points in or just before it                |
| `0x486D0A8F`                                | 1,525 | 0       | high-entropy bytes (*[INFERENCE]* a compressed or scrambled blob)                        |
| `0x486CFC43`                                | 641   | 17      | held by the tone generator's tables, read through no instruction the walk follows        |
| `0x48715746`                                | 458   | 0       | more of `func_48412A17`'s 128-byte records' tails, past its index bound                  |
| `0x48733632` / `0x48733428`                 | 774   | 0       | after `ChordRecogTable2`: *[INFERENCE]* chord-recognition rows read from a computed base |
| `0x485ED01C` / `0x485ECDA0`                 | 824   | 20      | records with pointers, held by typed records, read by none the walk sees                 |
| `0x485F95E0` (`HpFlashWriteDefaults_Table`) | 304   | 0       | the table's tail past the bound its reader checks                                        |

These are the walk's limits (*[INFERENCE]* on what they are): an address computed from a pointer
the walk does not carry across a loop iteration, a RAM pointer set at start-up, or a table read only
in a branch the linear walk enters with no state.

## Open

- Recursive structures besides the resource-id trie are typed one level deep: the walk sees one
  loop iteration.
- The 4-byte demo-stream events of `func_485831BA_Table`'s three streams are byte rows: the reader
  indexes `+0` of every 4-byte step, the other three bytes' readers were not traced.
- Records whose pointer fields point into their own tail (the switch descriptors) want a "record +
  inline payload" representation.
- An array's record count, where the readers check no bound, is where its records stop being free
  or another name begins; such counts are inferences, listed in each macro header.
