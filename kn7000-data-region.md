# KN7000: the program's data region, typed from the code that reads it

Program build 941's data region is file `0x186000`..`0x3B8B78` (CPU `0x48586000`..`0x487B8B78`):
2,304,888 bytes of tables, records, text, pictures and compressed songs between code region 1 and
the MILK kernel's flash tail ([Firmware Images]({{ site.baseurl }}/kn7000-firmware/#region-map)).
Until 2026-10-30 it ran on to the library image at `0x3B8FD1` (2,306,001 bytes); the last 1,113 of
those bytes are code ([below](#the-kernels-flash-tail)). Until 2026-10-29 the
disassembly held it as three `.incbin_range` lines and a typed palette. It is now
`kn7000/src/program/data/`, generated by `kn7000/tools/gen_data_s.py`, and the image stays
byte-identical (`make -C kn7000 verify`). Builds 942 (SP7001), 935 and 893 get the same from the
same generator (`--profile sp7001 / b935 / b893`, `src/<build>/program/data/`,
`make verify-sp7001 verify-935 verify-893`).

The GUI part of the region, the 8,509 widget records and their classes, is on
[KN7000 Menu Map]({{ site.baseurl }}/kn7000-menu-map/). This page covers the rest. The lanes of
the data-semantics effort did the work; their notes, in the disassembly repository, are the
reference:

## Structures that have a format of their own

- **The built-in demo songs.** The 30 zlib streams of each build are its 10 demo songs, three
  streams each. `func_48457350` (d0 = the song) takes song n's streams from three 12-entry tables
  in the initialised RAM and inflates them with `func_48533758`: the song record into
  `Rec8E0TablePtr(0)` (`0x8E0` bytes), the event memory into `0x5003D36C` (`0x9800` bytes) and a
  panel-memory bank. They are the formats of the floppies' `.SQT` and `.PMT` files, so the floppy
  describers type them, event by event and record by record
  ([Floppy Disk Files and Formats]({{ site.baseurl }}/floppy-disk-formats/#songs-sqt)), inside
  `.zlib 6` blocks: kn7asm compresses them with Python's zlib, which reproduces all 30 streams
  byte-exactly.
- **The program's own "Technics Rhythms" resource.** `TechnicsRhythmsResource` (941 `0x48729988`)
  has IC18's format ([Rhythm ROM (IC18)]({{ site.baseurl }}/kn7000-rhythm-rom/)) with a single
  style, "8 Beat 1", the fallback. `tools/program_rhythm.py` types it with IC18's macros: header,
  count block, the 2048-entry index, the tables, the 8 count-in patterns, the style record and its
  20 variations, every event one line.
- **Built-in panel memories.** The `0x486C`..`0x4870` region holds 103 (941) built-in PANEL
  MEMORY records: tag / length lists that start with the name record, hold 43 records and fill
  exactly `0x750` bytes, several behind a 16-character bank name. They are `PMR_*` lines, the same
  macros as the floppies' `.PMT` files ([Panel Memory Records]({{ site.baseurl }}/kn7000-panel-memory/)).
- **The tone generator's curves.** The region `0x486C0000`..`0x486F0000` is not style data: it is
  the tone generator's curve and level tables, read by the `Tg*` library routines
  (`TgElemNoteOnStd_Table` is the curve at `0x486D1F54`, 128 x u16).
- **The effects-DSP download records**, 80 of them, block by block, each program-memory word with
  its SHARC instruction ([Effects DSP]({{ site.baseurl }}/kn7000-effects-dsp/)).
- **Bitmaps.** Procedures that answer `MT_GetBitmapData` / `Width` / `Height` / `Palette` /
  `MT_GetBitCount` give the bitmap resources, and pixels handed to `DrawBitmapSP` and its variants
  with a constant size give more; they are indexed PNGs in `<data dir>/media/`, packed back by
  `tools/table_png.py` at build time. The 8 JPEG and 2 BMP files the region holds are whole files.

## Typed from the code that reads it

Most of the region has no format of its own: it is tables and records that only the code
explains. `kn7000/tools/data_readers.py` walks the converted code function by function, with a
symbolic value per register:

| value      | meaning                                                                            |
|------------|------------------------------------------------------------------------------------|
| `C(c)`     | a constant                                                                         |
| `A(x)`     | the address x (a data label, `Label+N`, or a number)                               |
| `S(s)`     | an unknown index times s (`mul` / `mulu` by a constant, `asl`, `asl2`, `add r, r`) |
| `I(b,s,o)` | b + index * s + o: field o of an array of s-byte records at b                      |
| `P(key,o)` | a pointer loaded from the 32-bit field `key`, plus o                               |
| `D(key,o)` | a function's own d0 / d1 argument: a pointer if it is dereferenced, else an index  |

Every load, store and call argument through such a register is an access, with its width and
signedness (an `extb` / `exth` right after the load). A function's accesses through its own
arguments are carried into every caller that passes a data address in them, so a record handed to
a helper is typed by what the helper reads. Every structure found is also checked against the
bytes.

**Struct arrays.** An access through `base + index * stride + offset` makes an array of
`stride`-byte records at `base`. Each record kind is one macro in `<data dir>/data_structs.inc`,
whose header lists every field, its type and its first readers, with the instruction:

```
# MusicStylistSetup: 24-byte records (StyleRecordTable, 1080 records); fields, and what reads them:
#   +0   panel        ptr            func_4847B18C 0x4847B18C `mov (d2, a2), a0`; AcCategoryListBoxProc 0x4847B2AE `mov (d0, a0), d0` (+10)
#   +4   name         ptr            MssNameFunc 0x4847AFDD `mov (4, a0), a1`; func_4847B14B 0x4847B14B `mov (4, a0), a1` (+3)
#   +8   genre        u16            AcCategoryListBoxProc 0x4847B2AE `movhu (8, a1), d0`; func_4847BA42 0x4847BA42 `movhu (8, a1), d0` (+9)
#   ...
#   +22  x22          u8[2]          no reader seen
```

**Records a pointer leads to.** When the code loads a pointer from a typed field and reads through
it, the targets of that field are records too, typed by the offsets those reads use. When the
targets lie a constant distance apart, that distance is the record size. `StyleRecordTable`'s field
`+0` points at 1,037 records of 160 bytes, one per built-in style's panel settings
(`MusicStylistPanelData`). Fields no traced reader names keep offset names (f / p / s / a / x +
offset), with every reader in the macro header; `tools/data_struct_names.py` names the kinds whose
role is known.

**The extended walk** (lane kn7000-final, `Reader(ext=True)`, the four KN7000 program builds only)
follows what the plain walk lost:

| rule              | what it follows                                                                                                | example                                                                                 |
|-------------------|----------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------|
| stack slots       | `mov aN, (8, sp)` ... `mov (8, sp), a0`: a slot keeps the value stored                                         | `func_484C4229` spills a value block to `(0x2c, sp)` and reads it with `movbu (a0), d2` |
| joins             | a label that paths reach with different data addresses holds "one of them"; reads through it are reads of each | `func_484C01F1`, a 260-way switch that leaves one descriptor's address in `(0, sp)`     |
| return values     | what a function returns in a0: one of a set of addresses, or a pointer loaded from a typed field               | `func_484C01F1` (260 records), `SoundAlphaListGet` (an entry of `SoundAlphaListTable`)  |
| named loop labels | a label is a function start only at its header, or where nothing falls in and no branch reaches it             | `DrawIcons_Impl_RowLoop` keeps a3 = `DrawIcons_PixelPairTable`                          |
| loop bodies       | a label reached only by a backward branch keeps the frame's slots                                              | `SoundAlphaIndexBuild`'s `movbu (d1, a0), d2` over a sound list                         |
| bounds            | a load whose source the walk does not know drops the bound an earlier `cmp` gave the register                  | `DrawIcons_PixelPairTable` is 256 entries, not the 240 of `cmp 0xf0, d0`                |

On program 941 the plain walk sees 22,372 distinct accesses and the extended one 26,677
(`kn7000/notes/data-final-probes/reader_ext_stats.py`); 126 functions return one of a set of data
addresses.

With it come new passes of `gen_data_s.py`:

| pass              | what it types                                                                                                         | evidence                                                         |
|-------------------|-----------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------|
| `support_classes` | the SupportClass table (registry slot `0xD`, 54 entries and an empty one) as `SUPPORT_CLASS proc, x4, propsize, data` | `InitSptClassTable` registers it; `SupportClassProc` reads it    |
| `resource_trie`   | the resource-id trie: 177 tables, 940 entries, 7,400 bytes, as `RES_TRIE_ENTRY target, inner, count`                  | `func_4C01BB1A`: nibble-indexed 8-byte entries, inner 0 = a leaf |
| `sysex_strings`   | MIDI SysEx messages a typed pointer points at (`0xF0`, data below `0x80`, `0xF7`; `0x50` = Matsushita), one row each  | the framing, and the pointer fields that hold them               |
| `copied_blocks`   | a data address passed to memcpy / memcmp / strncmp / strncpy with a constant length: that many bytes                  | the call's a0 / a1 and d0, cited in the header                   |
| `pointer_runs`    | aligned runs of 3 or more words that are each 0 or an address of the region: `.long Label`                            | *[INFERENCE]* by value; the header says no reader was traced     |
| `ptr_records`     | records one function selects: `<func>_Result` / `<func>_Selected`; short records as `<kind>_s<N>` size variants       | the reads through the selected value                             |

**The resource-id trie** is the table every live panel parameter goes through: `GetM3Em` /
`PutM3Em` look a 24-bit parameter id up in `ResourceIdTrie` (`0x4858B424`, inside the typed
`ResourceIdTrieNode_485897BC`), a tree indexed by the id's nibbles, whose 469 leaves say which byte
of the live panel record holds the parameter. What those leaves name is on
[Panel Memory Records]({{ site.baseurl }}/kn7000-panel-memory/).

Other examples: `TechniChordCompute_Table_2` is the chord-type switch of `TechniChordCompute`
(`0x48472EBA`), 42 code pointers (a table that holds code addresses spells each target `loc_<ADDR>`,
and `code_refs.txt` makes the code generator label it); the effect names and fixed-width value
strings ("  0.1   ", "   10 ms") are string arrays; `{u32 key, code address}` runs are dispatch
tables, with a MILK-id key spelled by its name.

## Sound lists, zlib's tables and field names (lane mn10300-formats)

Lane mn10300-formats (2026-10-31, [`kn7000/notes/mn10300-formats/README.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/mn10300-formats/README.md)) took the last open data-format items of the
MN10300 trees. Its KN2400 and KN6000 findings are on their pages
([the model strap and the effect descriptors]({{ site.baseurl }}/kn2400-program-data/#the-dsp-effect-descriptors-lane-mn10300-formats),
[the sound hash payloads]({{ site.baseurl }}/kn6000-program-data/#the-built-in-sound-hash-tables-kn6000));
the KN7000's are here and on [SP7001 Plug-in]({{ site.baseurl }}/kn7000-sp7001-plugin/#open).

### The alphabetical sound lists

`SoundAlphaListTable`'s lists were described here as demo-song streams of 4-byte events. **They are no
demo songs.** `SoundAlphaIndexBuild` (`0x485831DC`) reads `+0` of each 4-byte entry and groups the
entries by that byte with the C library's ctype table (letters first, then digits), and
`SoundAlphaInitialGet` (`0x485834C0`) matches `+1` / `+2` / `+3` against a sound's bank MSB, LSB and
program and answers `+0`. So an entry is {char initial; u8 bank MSB, LSB, program}, a list ends with a
zero entry, and `SoundAlphaListGet` (`0x485831BA`) picks one of the table's 6 pointers by kind (the
sound group) and a variant. The four lists (941):

| label                             | entries | selected for                           |
|-----------------------------------|---------|----------------------------------------|
| `SoundAlphaList_Groups00_12`      | 1,236   | groups 0..0x12 and 0x1F, variant 0     |
| `SoundAlphaList_Groups00_12_Var1` | 1,215   | the same groups, variant 1             |
| `SoundAlphaList_Groups13_1E`      | 1,210   | groups 0x13..0x1E but 0x19 / 0x1A      |
| `SoundAlphaList_DrumKits`         | 41      | groups 0x19 and 0x1A (the drum kits)   |

`gen_data_s.py`'s `sound_alpha_lists()` pass writes one `SOUND_ALPHA "A", 121, 2, 120` line an entry in
the four KN7000 program builds; the siblings have no such lists. Variant 1 is chosen when
`func_484974A4` answers 0 for the group *[INFERENCE on what it tests]*. The real demo-song streams are
the inflated ones whose tables sit in the initialised RAM at `0x50000C20` / `0x50000C50` / `0x50000C80`
([Work RAM]({{ site.baseurl }}/kn7000-work-ram/)).

### zlib's tables

`kn7000/notes/mn10300-formats-probes/zlib_tables.py` finds 19 of zlib 1.0.4's
data tables by their contents (they are the zlib sources' own) in every KN7000 build and in the KN6000,
KN6500 and KN2400; the HD-SX3 plug-in has no zlib. They are named at their RAM addresses (the
initialised-RAM image) in each tree's manual symbol file: `configuration_table`, `extra_lbits`,
`extra_dbits`, `extra_blbits`, `bl_order`, `static_l_desc` / `static_d_desc` / `static_bl_desc`,
`static_init_done`, `border`, `cplens`, `cplext`, `cpdist`, `cpdext`, `fixed_built`, the two copyright
strings, `inflate_mask` and `z_errmsg`.

## Pointers, arrays and loops (lane mn10300-typer)

Lane mn10300-typer (2026-10-31, [`kn7000/notes/mn10300-typer/README.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/mn10300-typer/README.md)) took the typer's open items: text typed as pointers,
the array-end rule, and four extensions of the reader walk. The machinery is in `kn7000/tools/`
(`gen_data_s.py`, `data_structs.py`, `data_readers.py`, `gen_program_s.py` and the new
`mn10300_insn_len.py`) and applies to every MN10300 tree. Each rule is a key of `gen_data_s.FEATURES`,
on by default; `GEN_DATA_S_OFF` turns rules off, which is how the lane's `typer_stats.py` measures each
one against the generator as it was:

| rule           | what it does                                                                                                                                |
|----------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| `ptr_starts`   | a 32-bit word is a pointer into code only when it is the first byte of an instruction; otherwise it is text or a number, as the readers say |
| `array_end`    | a pointer loop proven to stop at an address (`cmp End, aN` and a branch back) ends the array it walks                                       |
| `mem_ptrs`     | data addresses stored to a memory slot (a RAM global, a data word, a field of a record) and loaded back elsewhere                           |
| `loop_index`   | a constant in a data register a loop writes is the loop's induction variable at its head; a pointer plus a scaled index keeps the scale     |
| `step_arrays`  | a block a routine steps through (or indexes) by s >= 2 is an array of s-byte records                                                        |
| `deep_records` | a loop that walks records through their own field types every record of the chain; blocks the code copies whole are typed copies            |

**The array-end rule.** At `cmp End, aN` followed by a branch back, taken while aN < End, with aN
holding the array's base at the loop head and base + s at the compare, the array ends at End; the
table header cites the compare. Only bottom-tested loops count. 40 bounds in build 941, 16 tables
shortened: `MainMmmControl_Table` is 256 entries, not 260 (its +1024 / +1028 are `MainMmmControl`'s
two variables), and the code that named the bytes after a shortened table now names their own tables:
`movhu (func_4850DF34_Table+20), d0` became `movhu (FE_CmpMDelFstMeas_Table), d0`, one of the `FE_*`
menu fields' min / max pairs the table had swallowed.

slots in 941 and types no new byte in the KN7000 builds. (b) `loop_index` treats a loop's counter as an
index rather than its first value, and counts a loop that compares its counter with a constant
(`DrawBitmapSPFast16_Impl`'s palette index runs 0x20..0x2F). (c) `step_arrays` types a block a routine
is handed and steps through as an array of records (`DrawBitmapSPFast4_ArgSp24_*`, a palette of 4-byte
records); the count is the loop's when it is proven, else the block's extent *[INFERENCE]*. (d)

tables (`VoiceDirRemapFind`, `VoiceDirClassFind`, `VoiceDirIndexFind`, `VoiceDirRefFind`,

## Blocks a routine is handed

Much of the program data is never read where it is named: the code loads the block's address and
passes it to a routine (in `a0` / `a1` for a pointer, `d0` / `d1` for a number, the rest in the
caller's stack frame at +0x10, +0x14, ...; [calling convention]({{ site.baseurl }}/kn7000-firmware/#calling-convention)),
and that routine reads the fields. Since lane callee-walk (2026-10-30,
[`kn7000/notes/callee-walk/README.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/callee-walk/README.md))
the data sources follow the address into the routine, and into the routines it hands it on to, and
write the block as a record of what they read: one macro per (routine, argument),
`REC_<routine>_Arg<slot>`, whose comment names each field's reader, and a header on each block naming
the routine, its address, the argument and the call that passes it.

The walk already carried a callee's reads through its register parameters into its callers. Three
things kept such blocks as rows: arguments past the fourth, which go on the stack, were not followed;
a callee's read at +6 of its argument came back as a read of the fixed address Block+6, so each field
became a separate `_Var` / `_Table`; and the siblings' walk lost the address on its way to the call.
`Reader(callee=True)` (profile key `readers_callee`, on the four KN7000 program builds and the four
siblings) adds:

| rule                | what it follows                                                                                                                                             |
|---------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------|
| stack arguments     | a call records each word of its frame holding a data address or a parameter as argument `spN`; the callee's read of `(N + frame, sp)` is parameter `spN`    |
| named branch labels | `bne DrawString_DrawNow`: a branch to a named label that no `call` and no routine header names stays inside the function                                    |
| loop steps          | a parameter pointer stepped (`inc a0`, `add 2, a0`) between a label and a branch back to it is stepped by a loop                                            |
| jump-table cases    | a label nothing branches to after the function's `jmp (aN)` takes the addresses and parameters the dispatch held (*[INFERENCE]*)                            |
| layouts             | per (function, parameter): every access relative to it, its own and its callees', to a depth of 4 calls, and the calls that pass a fixed data address in it |
| siblings only       | frame slots (narrowed), address joins and return sets, the KN7000 extended walk's rules, so a switch that selects a record per case reaches the call        |

`tools/gen_data_s.py` then types a block as such a record when the routine reads at least two of its
fields (or one past +0), and says why when it does not (`arg_why()`): a library routine (`str*`,
`mem*`, `*printf`), a routine that only stores the pointer (a timer, a registry, a queue), a byte loop,
or one field at +0. Two records of a kind a whole number of records apart with free bytes between have
the records between typed too (*[INFERENCE]*). Fields are offset-named (`f12`, `p8`, `x4`) except where
`tools/data_struct_names.py` knows their use: the kernel's task-creation blocks are micro-ITRON
`T_CTSK` records {`exinf`, `tskatr`, `task`, `itskpri`, `stksz`} that `cre_tsk` (`0x4C03D0C8`) hands to
`func_4C03D154`; before, each field was a separate one-word table. Other examples:
`REC_func_4C03C7EF_ArgA0` (12 bytes, 10 blocks and one 8-byte variant), `REC_func_48401F32_ArgA0`
(28 bytes, with one record between two passed ones inferred), `REC_func_4844416A_ArgA0` (read at
+3..+5 after an `add 2, a0`).

### The kernel's flash tail

The generic-zero snapshot still declared one piece of code as data: `func_487B8E34`, 301 bytes the
library's `func_4C03B514` calls (`call func_487B8E34, [d2,a2,a3], 0x1c`), was
`census: opaque -- unknown-dump`, followed by more opaque pieces that were call targets
(`func_487B8F9B`, `func_487B8F9E`, `func_487B8FA1`) and a jump target (`loc_487B8FA4`). Lane
code-island (2026-10-30,
[`kn7000/notes/code-island/README.md`](https://github.com/ArqueologiaDigital/technics-roms-disasm/blob/main/kn7000/notes/code-island/README.md))
found why: the MILK kernel keeps 1,317 bytes in the flash, right before the library image the boot
copies, and the generator's split knew only two code ranges, code region 1 and the copied image.
Everything between was data, so the kernel's flash-resident routines fell in the data region, where
no instruction *loads* from them and the reader search declared them unread.

`gen_program_s.py` now walks every call and jump target the converted code has in the data region
by control flow, emits what it reaches (and the unreached runs up to the library image, which must
decode into code ending in a return or jump) as `src/<build>/program/tail_code.s`, and writes the
range to `<data dir>/tail_code.txt`; `gen_data_s.py` ends the data region there. In 941 the 1,113
bytes from `KernelInit` on are code, and the 204 bytes before them stay typed data:
`Str_MILK_MN10300_Ver1_0R1`, `KernelServiceHash`, `KernelRamLayout`, `KernelParams`. The old
`func_487B8E34` is `KernelWaitRelease_entry`, five bytes into `KernelWaitRelease`. Every routine, with
its evidence and its address in each build, is on
[Firmware Images]({{ site.baseurl }}/kn7000-firmware/#the-kernels-flash-tail).

**`func_4C03B799_Table`'s true extent.** `func_4C03B799` reads it four times, always as
`movhu (func_4C03B799_Table), dN`, with no index and no offset, so it reaches exactly one halfword,
`KernelParams + 0x16` (value 10). The two halfwords after it (30, 0) are the end of `KernelParams`,
which no instruction the walk sees reads. The table had been typed "353 x s16" because
`reader_tables()` runs a fixed-address read up to the next label, and the next label was the call
target `func_487B8E34`, 706 bytes on: entries [3] .. [352] were the 695 bytes of `KernelInit` and the
5-byte prologue of `KernelWaitRelease`. (The many 20,536 = `0x5038` halfwords in it were the high
halves of `KernelInit`'s `mov 0x5038xxxx, aN` immediates.) It now reads `3 x s16, 0..30`, its header
saying which index is read; `func_4C03B514_Table` next door is two halfwords of `KernelParams` the
same way.

The opaque census fell by 8 pieces / 507 bytes in each of the four builds (the tail's 7 pieces and
the 94 bytes before them). The same lane gave the MN10300 siblings' generator the encodings it had
left as `.byte` escapes (278 instructions; branch targets landed on them), so no sibling has a `.byte`
run in its code any more. Its probe,
`kn7000/notes/code-island-probes/code_in_data.py`, lists every branch target, code-named label,
fall-through and code pointer that lands on bytes a tree emits as data: after the lane, none in any
MN10300 tree except struct fields that hold text which reads as a code address
(`REC_StartFeatureDemo_Table_p0`'s `p28`, the `"><SH"` of the feature demo's XML script) and two
words of the KN2400 typed as pointers by value. Since lane mn10300-typer none at all: its P column
(mid-instruction `.long`s) is 0 in every tree ([above](#pointers-arrays-and-loops-lane-mn10300-typer)).

**Opaque** (`census: opaque -- unknown-dump`) means that no load, store, base or call argument of
the converted code lands in the bytes under the extended walk, and the line says whether a typed
pointer or a code immediate still holds their address. `kn7000/notes/data-final-probes/opaque_holders.py`
also searched the whole image for any 32-bit word, at any alignment, holding an address in the
piece or up to 64 bytes before it. The biggest in 941:

| piece                                       | bytes | holders | what the bytes look like                                                                 |
|---------------------------------------------|-------|---------|------------------------------------------------------------------------------------------|
| `0x48730AB3`                                | 2,101 | 0       | 7-byte groups `xx 90 xx xx xx 00 00`; no word points in or just before it                |
| `0x486D0A8F`                                | 1,525 | 0       | high-entropy bytes (*[INFERENCE]* a compressed or scrambled blob)                        |
| `0x486CFC43`                                | 641   | 17      | held by the tone generator's tables, read through no instruction the walk follows        |
| `0x48715746`                                | 458   | 0       | more of `func_48412A17`'s 128-byte records' tails, past its index bound                  |
| `0x48733632` / `0x48733428`                 | 774   | 0       | after `ChordRecogTable2`: *[INFERENCE]* chord-recognition rows read from a computed base |
| `0x485ED01C` / `0x485ECDA0`                 | 824   | 20      | records with pointers, held by typed records, read by none the walk sees                 |
| `0x485F95E0` (`HpFlashWriteDefaults_Table`) | 304   | 0       | the table's tail past the bound its reader checks                                        |

These are the walk's limits (*[INFERENCE]* on what they are): an address computed from a pointer
the walk does not carry across a loop iteration, a RAM pointer set at start-up, or a table read only
in a branch the linear walk enters with no state.
